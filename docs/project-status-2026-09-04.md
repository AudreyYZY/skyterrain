## 2. 这次外部评审反馈的评估结果

用户转发的评审分五部分：真实数据现状、亮点、不足、有没有受众、定位建议。逐条评估：

### 2.1 必须修的（已修，见 §3 提交记录）

1. **README / README_EN 数字过期**——914/379/209/33 国，全部改成当前真实值
   （1041/467/295/38 国），并把大段容易再次过期的"按国家累加地形数"明细替换成
   指向 `CLAUDE.md`"范围"一节的引用（那里才是持续更新的权威源，不再维护第二份
   会飘的副本）。
2. **`docs/routes.md` / `docs/architecture-metrics.md` / `docs/architecture.md`
   数字/内容过期**——三份都是早期快照（`architecture*.md` 两份是 2026-06-30
   codeatlas 生成，`architecture.md` 那份甚至还在描述早就删除的"照片识别地形"
   功能）。**没有逐字修正内容**（那样等于重写，尤其 `routes.md` 整篇分析是围绕
   "只有 4 条航线"这个早就不成立的前提展开的）——改成在每份文档顶部加醒目的
   "已过期"横幅，说明过期到什么程度、权威源在哪，保留原文作历史记录。
3. **`package.json` 缺 `"type": "module"`**——每次跑 `node --experimental-strip-types
   scripts/*.ts` 都会打一条"reparsing as ES module"警告。确认过没有任何 `.js`
   文件依赖 CommonJS 语法（配置文件都已经是 `.mjs`/`.ts`）后直接加上，构建/自检
   脚本全部重跑确认无回归。
4. **`check-routes.ts` 的"航程与时长不匹配"警告是误报**——旧公式假设全程按
   800km/h 巡航速度算，对 200~500km 的短途航线（真实时刻表里爬升/下降占比很高，
   均速本来就远低于巡航速度）系统性误判，23 条真实、已核实的短途航线因此被
   标黄。改成"固定地面/爬升/下降开销 + 巡航段"的估算模型后重跑，23 条误报
   全部清零，检查仍能正常工作（这只是 console 提示，从来没计入 0 项异常的
   失败判定，所以不影响之前任何一次"0 项异常"的结论）。

### 2.2 认可但不在本次动手范围内的（已记录，留给用户决定何时启动）

这些是真实存在的问题，但要么风险大、要么本质是产品方向决策，不适合在处理
"评审反馈"这个任务里顺手做掉：

1. **God Component**：`ExplorerApp.tsx`（现 1421 行）、`CesiumMap.tsx`（现 1483 行，
   `wc -l` 实测）确实偏重。评审建议的拆分方向（`CameraController` / `FlightController`
   / `DebugOverlay` 等）合理，但这是一次跨越核心交互链路的重构，做错了容易
   引入难查的回归（这两个文件正是相机飞行、语音同步、地图交互全部汇聚的地方）。
   不在没有专门规划+测试计划的情况下动手。
2. **类型模型未统一**：`TerrainPoint`（早期）/ `GeographicFeature`（次世代）/
   `TerrainEntry`（当前单一真实源）三者共存，中间靠桥接转换。`TerrainEntry` 事实上
   已经是当前唯一被写入的模型，`TerrainPoint`/`GeographicFeature` 主要是历史遗留的
   读取兼容层——评审说的"迁移中的技术债"准确，但清理它需要先确认没有隐藏消费方，
   属于独立的清理任务。
3. **数据核实程度不均**：`source` 字段有相当一部分写的是"概略"而非可复核的具体
   来源，个别条目明确标"待实测"。这是规模扩张的正常代价（1041 处地形、467 座
   城市不可能每条都做到国测局公告级别的核实），项目里已有的应对方式是
   "source 留痕、不作为质检认证"——评审的观察准确，但"统一提高核实深度"不是
   一次性能做完的任务，是持续的内容质量工作，已经在按批次进行（比如
   `docs/expansion-playbook.md` 记录的历次批次都要求 WebSearch 核实）。

### 2.3 战略性反馈——不是代码问题，是产品方向问题，需要用户自己决定

评审最后"有没有受众"和"定位建议"这部分，评估下来是**这次外部反馈里最有价值、
但也最不该由我单方面拍板的一条**：

> 评审的核心论点：这个项目现在打不过、也没必要打"旅游攻略平台"这个赛道
> （旅游模式目前是城市攻略概览级，缺路线/预算/季节/停留天数/偏好/实时信息，
> 论"攻略详尽度"拼不过携程/Lonely Planet 这类产品）。更清晰的定位是**"给坐飞机、
> 学地理、做旅行内容、教地理的人看的空中地貌讲解器"**——护城河不是"城市攻略
> 更多"，是"这条航线窗外那片山/河/平原是什么、怎么形成的、为什么城市在这里"。
> 建议：每条航线做成"一集短纪录片"级别的深度，每座城市讲清"地形如何塑造
> 城市"，先把一两个高强度场景做深（评审举例：中国进藏航线地貌课、日本国内
> 航线看火山/平原/海岸、留学生/游客第一次理解澳洲地貌），而不是继续往
> 1000+ 城市这个方向堆数量。

这个判断跟项目自己的产品定位文档（`CLAUDE.md`"产品定位"一节：
"不是 GIS 仪表盘，不是飞行模拟器，不是游戏"）方向是一致的、甚至是把这个定位
说得更彻底——但**"下一步该堆广度还是转向做深度"是一次真正的产品路线决策**，
不是"修 bug"性质的任务，我没有替用户做这个决定，也不建议下一个接手的会话
自行决定。**这是本文档最想传递给后续任务的一条信息：如果用户没有明确表态，
默认继续走当前"按国家扩张广度"的路线（`docs/expansion-playbook.md` 记录的
一贯做法），不要因为看到这份总结就擅自转向"做深"方向。**

## 4. 这次会话（2026-09-04）另外完成的功能性工作

跟这次"评审反馈修复"任务并行/在此之前完成，供后续任务参考、避免重复劳动：

- **中国 Tier2 骨架收尾**：9 个此前只有省会的省级行政区各补 1 座城市，
  中国旅游模式城市数 64→73。
- **澳大利亚 Tier2 骨架收尾**：8 个州/领地全部满足"≥2 城市"（补吉朗）。
- **中国国际航线骨架**：35 个已收录国家中 32 个有真实直飞航线（3 国如实
  标注缺口：卢森堡/冰岛/克罗地亚查无真正不经停客运直飞）。
- **旅游目录改按官方一级行政区（省/州）分组**：大区（华北/华东等）降级为
  分组标题旁的彩色圆点提示；圆点配色改沿色相环连续过渡（原先固定调色板
  按索引取色，相邻大区可能跳到不相关色相）；分组排序改按省/州拼音/字母序
  （原先按大区顺序，找省份没有直观依据）；全局搜索现在也匹配省/州名。
  覆盖全部 38 个国家（China 已有的省级行政区数据 + 其余 37 国分批 WebSearch
  核实真实省/州归属）。
- **旅游模式首页加大洲选择**：原来只有学习模式能在首屏选大洲，旅游模式
  只能沿用上次选的大洲；改成两种模式共用同一个大陆滑动选择组件，卡片显示
  准确城市数（不是硬编码）。副作用：顺带排除了旧版"已看过引导页就静默
  跳过"逻辑——这是本项目反复出现的"没等用户选择就自动跳转"bug 的根源
  之一，现在从组件设计上排除，不再只靠约定。
- **航线飞行加地形/地标停留**：原来镜头位置纯粹是"解说进度 × 总距离"的
  线性映射，短途和洲际航线解说时长差不多长，长航线镜头因此飞得快很多、
  地图瓦片来不及加载，画面糊；且镜头从不真正停下，飞越每个地形只是一晃
  而过。改成给每个地形/地标航点插入一段"镜头不动、等时间到了才继续走"的
  停留区间，停留时长按每条航线的解说时长自动换算（不用给 295 条航线逐条
  调），且严格保持"解说播完镜头也刚好飞完"这条约束不变。
- **TTS 长文本英文合成超时**：8s 超时是按短文本（travel guide 单段字段）
  校准的，航线解说是整段不分段发送、英文常 700-1400 字符，导致合成几乎
  必然超时一次才成功。调到 13s 后验证过的失败项全部一次成功。顺带修了
  同一个文件里一个肉眼不可见的裸 NUL 字节编码 bug（导致 git 一直把这个
  文件当成二进制文件、diff 显示不出来）。

以上工作均已验证（`tsc`/`build`/自检脚本）并合并到 `main`，对应 PR 见
git log（`#103`–`#125` 区间，具体号码以 `git log --oneline --merges` 为准）。
