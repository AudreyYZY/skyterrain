# 内容流水线：加一批城市 / 地形 / 航线的标准流程

> **这份文档是流程的唯一定义。** 新会话接手「继续加城市 / 地形 / 航线」这件事时，
> 从这里开始，不需要用户再口头交代一遍要测什么、要不要等审批。
> 机器版是 `npm run gate`（`scripts/gate.ts`），两份东西描述的是同一个流程。
>
> 立这份文档的原因（2026-09-18，用户原话的意思）：
> 「加完内容之后要审核、要检查出问题、要改、CI 要绿」这些步骤此前只活在会话记忆里，
> 于是**每开一个新会话都要重新交代一遍**；而且同一批问题反复出现 ——
> 高亮跟不上语音、播报是机械音、新内容没抽查过。
> 这些都不该由用户点开某个城市时撞见，**应该在加完那一批的当天就被拦下**。

---

## 一句话版

```
G0 安全前置 → G1 研究 → G2 写入 → G3 生成 + 静态门禁 → G4 预热 + 批次门禁
   → G5 内容核实 → G6 代码审查 → G7 提交 → G8 CI 到绿 → G9 记账
```

**不需要等用户审批**（2026-09-17 用户明确授权）。但 **G3–G8 一项都不能跳**，
其中任何一项没过就不提交；查明有问题却当轮修不了的，**必须留成 GitHub issue 再往下走**。

---

## 为什么是这些关卡：每一关都对应一次真实的翻车

| 用户实际报过的问题 | 根因 | 现在哪一关拦它 |
|---|---|---|
| 「语音已经念到后面了，高亮还停在前面，很迟钝很卡」 | 面板与高亮用了两份切句实现；长句一块停 15 秒 | G3 `check:sentence-split` + G4 `check:batch` ② |
| 「测试时听到的还是不自然的 AI 播报声音」 | 新内容没预热 → 现场合成超时 → 整篇降级成浏览器 TTS | **G4 `check:batch` ①**（硬失败） |
| 「航线飞行的时候画面很糊、很抖」 | 取景高度/地速比、帧率驱动 | G3 `check:flight` |
| 「新加的内容没有做过校对和抽查」 | 核实只在有人记得时才做 | G5（流程内必做）+ G9 定期均匀抽样 |
| 「CI 通不过，没法 merge」 | 本地只跑了一部分检查 | G3+G4 与 CI 同一套，G8 盯到绿 |

**这张表就是这份文档的存在理由**：五类问题全都不是「没有防线」，
而是**防线没在正确的时间、对正确的范围跑**。

### 反复出现的那个坑，单独说

**全库口径的平均数与固定抽样，都会把「新加的那一批」漏掉。**

- `check:tts` 的覆盖率是全库平均、且**不判失败** —— 一整批 0% 命中藏在 99% 的平均数里；
- `check:highlight-sync` 抽的是 `CITY_REGISTRY.slice(0, 40)` —— 注册表按国家排序、
  新内容追加在末尾，**它永远只看第一个国家的前 40 条，一次都没看过任何新内容**。

用户报高亮错位的那天，这两个脚本都在跑、都「通过」了。
所以 2026-09-18 加了 **`npm run check:batch`**：从 git diff 反算这一批动过哪些条目 id，
逐项只看这些条目，并且**逐项报出实际检查了多少个对象**。
（`check:highlight-sync` 的头部抽样同日改成跨步抽样，让每个国家都进得来。）

> 写任何新检查时照这条判据自问一次：**它看得见新加的内容吗？**
> 看不见的检查，通过了也不说明任何事情。

## G0 安全与选题前置

1. **先取英国外交部（FCDO）该国旅行建议页**，记下更新日期。
   - 劝阻前往全国 / 大部分地区、或处于武装冲突 → 整国暂缓；
   - 有地区级劝阻 → 劝阻地区及其 **20 km 内**的城市 / 地形 / 航线一律不收；
   - 另按既定做法：白俄罗斯 / 俄罗斯 / 乌克兰这类正文本来就不能写的边境，其 20 km 内同样不收。
2. 执法机构通报的大规模跨境电信诈骗、人口贩运集中地区 → 不发布旅行导向内容。
3. 来源矛盾、变化过快、无法中立表述 → 暂缓，**不要硬写**。
4. 零争议红线：现代政治 / 领土 / 族群 / 宗教评价一律不碰；跨境地形按「交界一带」中性表述。

详见 `docs/expansion-playbook.md` §2.1 与 CLAUDE.md「发布门槛」。

## G1 研究

- 用 `general-purpose` 子代理产出一份**事实表**落到 scratchpad，不要边查边写正文。
- **请求头里不要放任何个人信息**（User-Agent 用通用字符串）—— 每个研究 / 核实子代理的
  prompt 里都要带这句。
- 来源分级：1 级 = 该国官方（统计局 / 地质调查 / 国家公园 / 民航局）与 UNESCO；
  2 级 = 权威百科、学术；3 级 = 其他。**1 级拿不到就如实写「拿不到」**，不要用 3 级凑。
- 数字要连**年份 + 口径 + 发布机构 + 发布月份**一起记；发布月份顺手补进
  `docs/data-refresh-calendar.md`（那是「这个数什么时候过期」的唯一索引）。
- **人口数字要逐位自检**：把同一张表里本库已有的几个条目拿来对，对不上说明取错了表。

## G2 写入

按国家目录写 `lib/content/<country>/{registry,terrain.zh,terrain.en,cities,pois,travel.zh,travel.en,routes}.ts`。

硬性习惯（CLAUDE.md 规则 ①–⑬ 的执行清单，写的时候逐条过）：

- [ ] 数字带**年份 + 口径 + 机构简称**，完整公报名只进注释（正文会被 TTS 念出来）
- [ ] 口径**先确认该国官方统计里存在**（「都会区人口」在中国不存在）
- [ ] 是**最新一期**（N 年数据一般 N+1 年上半年发布）
- [ ] 最高级 / 排名给限定语，否则不写（`check:claims` 基线 0，写了直接失败）
- [ ] 「没有机场」写成「没有定期航班的机场」（中国条目写「没有民用机场」）
- [ ] 不写机场航点列表、不写签证天数、价格带年份
- [ ] 英文多段拼接时，上一段以句号结尾则下一段以空格开头
- [ ] 新城必须写 `howItWorks`，且**主线是本库还没写过的结构层次**
- [ ] 每个条目带 `sources` 注释 —— **没有注释 = 没核过**，这是唯一机器可读的凭据
- [ ] 排他性断言（唯一 / 首座 / 最大）先在**本库同国家条目里搜一遍**再写

## G3 生成 + 静态门禁

```bash
npm run gen:content          # 改了内容目录必跑，_generated/ 不要手改
npm run gen:anchors          # 只在改过航线解说文字之后
npm run gate -- --stage=1
```

第 1 段包含 `check:content` / `check:sentence-split` / typecheck / lint /
`check:regions` / `check:camera` / `check:places` / `check:routes` / `check:claims` /
`check:flight` / `check:anchors`。**`check:claims` 是棘轮**：新写一句没年份的人口数就会失败。

## G4 预热 + 批次门禁 ← 这一关是 2026-09-18 新加的

```bash
npm run warm:tts -- --ids=<这批新增的 id，逗号分隔>
npm run gate -- --stage=2     # 等价于 npm run check:batch
```

`check:batch` 自己从 git diff 算出这一批动过哪些条目（`--base=` 可指定基准，
`--ids=` 可手工指定），然后只看这些条目：

| | 检查什么 | 为什么是硬失败 |
|---|---|---|
| ① | 这一批的播报**全部**已在 `.tts-cache/` | 没命中就要现场合成，中文冷合成约 19 秒；`section-narration` 连续 2 段失败就**整篇降级成浏览器 TTS** —— 那就是用户听到的机械音 |
| ② | 拿**真实 word boundary** 跑生产时间映射：单调、不重叠、覆盖 ≥90%、没有 >13 秒的块 | 这就是「高亮跟不上语音」的直接度量 |
| ③ | 条目有 `sources` 留痕（上方或块内） | 报告项。没留痕的条目下一轮会被当成从没核过 |

> **它第一次跑就抓到了一处真的**：批 18 的 `toktogul` 有 2 段在预热之后被改过、没有重新预热 ——
> 用户点开那一条听到的就会是机械音。这正是这一关要拦的东西。

## G5 内容核实

```
/verify-content            # 或直接开 content-verifier 子代理，每批 8–12 个条目
```

- 流程细节见 `.claude/skills/verify-content/SKILL.md`（红线、prompt 该写什么、findings 格式）。
- **拿不准记 `unknown`，不要补一个看起来合理的答案。**
- `unknown` ≠ 原样留着：已经查明写法有问题的，**先把有问题的表述删掉**，issue 继续开着。
- 应用结论：`npm run verify:apply-text -- <findings.json>`（正文）/
  `npm run verify:apply`（航线字段）→ 再 `npm run verify:report`（开 / 关 issue + 记台账）。
- 改完**回到 G3 重跑第 1–3 段**（改了航线解说还要 `gen:anchors`）。
- 第 3 段的内容交叉检查在这一步之后最有价值：

```bash
npm run gate -- --stage=3    # check:zhen / check:distance / bearings / airports / rvt / pending
```

`check:zhen` 是「只改了一侧」的唯一防线（中英是分开写的，人核实时又是按语言读的）。

## G6 代码审查

**只要这一批动过 `components/` / `lib/` / `scripts/` 下的代码（不只是内容文本），就必须做。**

- 跑 `/code-review`（本地多角度审查）；改动较大或跨模块时用 `/code-review ultra`
  （用户触发的云端多代理审查，我不能自己发起 —— 需要就告诉用户这一条命令）。
- 这个项目的代码错误有一个**特有类型**，审查时专门看：
  **「两份实现各自都对，错的是它们不一致」** —— 类型能过、测试能过、两边都说得通。
  已经栽过的实例：`StructuredLesson` 自带一份切句实现；`section-narration` 的
  `baseIndex` 用 `splitSentences` 而面板用 `splitForHighlight`。
  判据：**同一件事有没有第二处实现？** 有就合并到一处，并加一条「不许有第二份」的检查
  （`check:sentence-split` 就是这么来的）。
- 第二个特有类型：**检查看不见新内容**（见上文「反复出现的那个坑」）。
  审查任何 `check:*` 脚本时问一句：它的取样范围包含新追加的条目吗？

## G7 提交

**业务代码 / 内容与文档分两个 commit**（开发规范）：

```bash
git add lib/content data/routes           # 或 components lib scripts
git commit -m "feat(travel): …"
git add docs CLAUDE.md
git commit -m "docs: …"
git push
```

提交前最后一道：

```bash
npm run gate                  # 全四段，第 4 段 = build + Playwright，与 CI 等价
```

**在 `main` 上则先切分支。** 提交信息末尾带
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`。

## G8 CI 到绿

- 推完**盯着 PR 的 CI 跑完**，不是推完就算完（用户明确要求：「CI 通过才完成提交」）。
- CI 跑 `npm run check` + `npm run build` + Playwright，与本地第 1、4 段同一套 ——
  所以本地过了 CI 还红，八成是环境差异（`.tts-cache/` 不进仓库，
  `check:highlight-sync` 在 CI 里自动跳过）。
- 红了就修到绿**再继续下一批**，不要把失败留在 PR 上开新批次。

## G9 记账

一批结束时这几处必须同步（漏了下一个会话就会读到过期的数）：

- [ ] `CLAUDE.md` 的计数（地形 / 城市 / 航线）与该国说明段
- [ ] `docs/city-expansion-progress-2026-09-05.md` 加一行（一批一行）
- [ ] 新错误类型 → `docs/known-errors.md` 新开一节 + 一个 `data-error` issue
- [ ] 查明有问题但**当轮没修**的 → **必须有 GitHub issue**（用户明确要求）
- [ ] 核实结论 → `docs/verification-ledger.md` + `lastVerifiedCommit`
- [ ] 「这就是最新一期」的结论 → `docs/claims-stale-exempt.json`，**并关掉对应 issue**
      （「查明拿不到数」是结论、不是待办）

**每推进几批换一个新种子做一次均匀随机抽样**（`npm run sample:claims -- --seed=19` 起，
17 已用过两次），结果记进 `docs/quality-sampling.md`。
这是**唯一**能回答「用户随手翻开一句，它错的概率是多少」的东西；
覆盖率口径有两层虚高，不要拿覆盖率当质量。**不要挑样本。**

## 常见失败与对应动作

| 症状 | 动作 |
|---|---|
| `check:claims` 某类计数上升 | 改写法（降最高级 / 补年份口径），不要改基线 |
| `check:batch` ① 有未预热段 | `npm run warm:tts -- --ids=…`，然后重跑 |
| `check:batch` ② 有 >13 秒的块 | 看是不是正文一句过长；`splitForHighlight` 的目标是每块约 5.5 秒 |
| `check:anchors` 句数对不上 | 改过解说文字没跑 `npm run gen:anchors` |
| `check:zhen` 报数字不一致 | 中英只改了一侧，两侧都改 |
| `check:content` 说生成文件没重跑 | `npm run gen:content` |
| e2e 超时 | 测试期间不要改 `components/` 下的文件（热更新会让地球重载） |

## 这个流程不承诺什么

本库 1352 处地形 × 6 板块 + 930 座城市 × 7 段 + 295 条航线 × 2 套解说的文字，
是**依据公开资料整理生成的，没有人逐条审核过**。
这套流程降低新内容的出错率（现行流程产出的新内容抽样 6.7%，旧流程 25%），
**但不把错误率降到零**。
所以任何对外文案都不要写「权威」「人工审核」「逐句核源」「真实商业航班」这类断言 ——
阅读面板底部的 `VerificationNote` 如实写每篇有多少段有核实留痕，
目标是让读者能自己判断该给多少信任。
